<critical_process_note>
Task 1 (plain `train`/`full` regression check) is a single pipeline run, ~30-90 minutes wall
clock per CLAUDE.md's documented timing. Task 2 (`arch-compare`) is a MUCH longer operation than
anything previously run in this project: 12 sequential full hierarchical-fusion pipeline runs (4
architectures x 3 regularization settings), each individually comparable in cost to one
`smote-ab` arm (~30-90 minutes per Phase 1's 01-03 observed timing). A reasonable estimate is
**6-18+ hours of total wall-clock time** for Task 2 alone. This is an explicit, deliberate choice
(per this phase's CONTEXT decisions): `arch-compare` runs as a SINGLE CLI invocation processing
all 12 arms sequentially in one process — not split into 12 separate resumable sub-invocations —
because `mode_train_ex()`'s per-arm RNG reseed (`rng_seed(RANDOM_SEED)` + `kfold_split()` at the
top of every call) already guarantees identical fold assignments across arms with zero manual
RNG snapshot/restore, and building a true stop/resume-from-arm-N mechanism would add nontrivial
CLI-argument/state-restoration complexity for no requirement this phase actually has. The
mitigation for this long single run is `mode_arch_compare()`'s incremental per-arm CSV append
(Plan 02-02): if the process is ever interrupted, completed arms' rows already exist on disk in
`results/arch_compare_comparison.csv`, even though the final `.txt` report (which needs all 12
in-memory) would not yet exist.

Given this, for BOTH Task 1 and Task 2: detach the process (`nohup`/`setsid`), redirect output
with `tee` (not just `>`) so progress is visible, and ACTIVELY POLL TO COMPLETION IN-TURN — do
not end the turn while either process is running, even across many `run_in_background`/Monitor
cycles or repeated Bash-tool foreground-timeout re-arms. This is the exact pattern Phase 0's
`00-01`/`00-03` and Phase 1's `01-03` plans already used successfully (up to ~136 minutes
continuously monitored); Task 2 here is 3-8x longer than any prior single run in this project,
which makes disciplined re-arming (never assuming a background process will "just notify you
when done" and ending the turn) more important, not less. If the Bash tool's foreground timeout
is hit while polling, immediately re-arm a new `run_in_background` monitor (e.g. `pgrep`-based:
`while pgrep -f "vocal_detect arch-compare" > /dev/null; do sleep 300; done`) rather than ending
the turn. Periodically `tail -50` the console-redirect file and/or check
`results/arch_compare_comparison.csv`'s line count (expect 1 header + up to 12 rows, growing one
at a time) to report intermediate progress. Do NOT fire-and-forget either task.
</critical_process_note>
</context>
